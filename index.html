Latency Comparison (Lower is Better)

Why is the difference so extreme?

PostgreSQL (Old Way): Every time your dashboard refreshes, the database reads through all 1.21 million rows, groups them by hour in a giant hash table, and sorts them. That burns 500+ ms of CPU time every single refresh.
TimescaleDB (Smart Way): Instead of recalculating everything on demand, TimescaleDB computes the hourly summary once as data arrives. When you query it, it only reads the 3,360 answer rows directly. That is why it takes 12 milliseconds!

Professor's Guide: Understanding This Project in 3 Steps

How to explain the core computer science breakthroughs to anyone without database jargon.

1

The Relational Trap

PostgreSQL was built in 1986 for things like bank accounts where you edit existing rows. When 20 IoT sensors stream readings every 10 seconds, it tries to stuff millions of timestamps into one giant index table.

Once that table gets bigger than the computer's RAM, the computer starts frantically reading and writing to disk, causing queries to stall.

Symptoms: Sluggish dashboards, 500ms lag.
2

Hypertable Chunking

TimescaleDB solves this by slicing the giant table into small, daily boxes ("chunks").

Today's data goes into today's box in super-fast RAM. Yesterday's box gets closed, turned on its side into columns, and compressed like a ZIP file (Gorilla compression). Old data takes 83% less space, and active writes never stall!

Result: Constant 28k+ rows/s insertion.
3

Continuous Aggregates

When a professor looks at a graph of hourly average temperature, PostgreSQL counts and calculates all 1.21 million numbers live on the spot.

TimescaleDB calculates the hourly averages incrementally in the background. When queried, it only reads the 3,360 pre-made answers, dropping query time from 518\,ms down to 12\,ms!

Result: 43.2x instant dashboard speedup.

Top 5 Viva Questions & Fast Answers:

Q1: Why did PostgreSQL have slightly higher bulk insert speed (29.1k vs 28.7k rows/s)?

PostgreSQL dumps straight into one flat table. TimescaleDB has to inspect timestamps and route rows into specific daily chunks. That routing takes a tiny 1.4% overhead, but it prevents crashes later.

Q2: How does Gorilla compression get an 83.5% space reduction?

Sensors log every 10 seconds. The time delta is always 10 seconds, so Delta-of-Delta is 0 (stored as 1 bit). Temperatures vary by tiny decimals, so XOR differences have matching prefixes and compress from 8 bytes down to ~1.5 bytes.

Q3: Why did PostgreSQL indexes take up 48.5% of total disk space?

Because standard B-Trees store row pointers and index keys for every single record. For small sensor rows, the index tree is almost as large as the raw data itself!

Q4: What is the downside of TimescaleDB chunk compression?

Compressed chunks are columnar and read-only. If you need to run frequent UPDATE or DELETE commands on historical data, you must decompress the chunk first.

Q5: Can we use regular SQL with TimescaleDB?

Yes! TimescaleDB is built directly inside PostgreSQL as an extension. You can run regular SQL SELECT, JOIN with student/inventory tables, and use standard drivers like psycopg2.
